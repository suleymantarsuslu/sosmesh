# ADR-008: BLE V1 Protocol Design

**Date:** 2026-10-29  
**Status:** Accepted  
**Deciders:** SOSMesh Team

## Context

SOSMesh requires a reliable, private, and efficient protocol for transmitting SOS messages over Bluetooth Low Energy (BLE) connections. The protocol must:

- Operate in low-bandwidth, high-latency, and potentially unstable network conditions
- Ensure message integrity and authenticity through cryptographic verification
- Support chunked transfer with resume capability for interrupted transmissions
- Maintain privacy by not exposing sensitive payload data to intermediate relay nodes
- Provide clear acknowledgment levels (peer received vs. server received vs. operator viewed)
- Be implementable across TypeScript, Kotlin (Android), and Swift (iOS) platforms

## Decision

We will implement BLE V1 Protocol with the following design:

### 1. GATT Profile

- **Service UUID:** `0000FFF0-0000-1000-8000-00805F9B34FB`
- **Characteristics:**
  - Control (`0000FFF1`): Handshake and control commands (Read, Write)
  - Data (`0000FFF2`): Chunk data transfer (Write)
  - Ack (`0000FFF3`): ACK/NACK responses (Read, Write, Notify)

### 2. Handshake Protocol

- **HELLO Message:** Sender initiates with version, nonce (16 bytes), and preferred MTU
- **HELLO_ACK Message:** Receiver responds with version, nonce echo, negotiated MTU, and status
- **Version Negotiation:** Both parties must agree on protocol version (0x01); mismatches are rejected
- **MTU Negotiation:** `chunk_size = min(sender_mtu, receiver_mtu) - ATT_overhead(3) - header(12)`

### 3. Chunking and Transfer

- **Chunk Format:** 12-byte header (seq, total, crc32, flags) + payload
- **CRC32:** IEEE 802.3 standard, big-endian encoding
- **SHA-256 Digest:** Last chunk includes 32-byte digest of complete assembled message
- **Flags:** FIRST_CHUNK (0x01), LAST_CHUNK (0x02)
- **Window-based Flow Control:** Maximum 4 chunks in flight, 2-second timeout per chunk

### 4. State Machines

**Sender States:**
- IDLE → HELLO_SENT → READY → SENDING → WAIT_ACK → VERIFYING → COMPLETED/FAILED
- RESUMING: Handles interrupted transfers by resending only missing chunks

**Receiver States:**
- IDLE → HELLO_RECEIVED → READY → RECEIVING → VERIFYING → COMPLETED/FAILED

### 5. ACK Levels and Critical Constraints

- **PEER_RECEIVED:** Generated ONLY after all chunks received, CRC validated, and digest verified
  - NEVER generated for incomplete or corrupted data
  - Does NOT mean "read by operator" (UI must use "yakındaki cihaza ulaştı" not "okundu")
- **SERVER_RECEIVED:** Generated by backend server after successful relay
- **OPERATOR_VIEWED:** Generated when emergency operator views the message
- BLE protocol layer NEVER generates SERVER_RECEIVED or OPERATOR_VIEWED

### 6. Resume Protocol

- **Resume Window:** 60 seconds after disconnect
- **RESUME_REQUEST:** Receiver sends bitmap of received chunks
- **Sender Behavior:** Resends only missing chunks based on bitmap
- **Idempotency:** Duplicate chunks are detected and deduplicated by receiver

### 7. Error Handling

- **CRC Mismatch:** NACK with reason 0x01, sender retries (max 3 attempts)
- **Digest Invalid:** FAILED state, NEVER emit PEER_RECEIVED
- **Total Mismatch:** FAILED state (sender/receiver disagree on chunk count)
- **Timeout:** Retry with exponential backoff + jitter (500ms random)
- **Version Mismatch:** HELLO_ACK rejection, immediate failure

### 8. Security and Privacy

**Envelope Structure (ADR-007 compatibility):**
```json
{
  "envelope": {
    "timestamp": "ISO8601",
    "location": {"latitude": 0, "longitude": 0},
    "priority": 1,
    "ackLevel": "PEER_RECEIVED"
  },
  "encryptedPayload": "BASE64_ENCRYPTED_SOS_TEXT"
}
```

**Privacy Guarantees:**
- Relay nodes can parse envelope but cannot decrypt `encryptedPayload`
- BLE transfer operates on serialized binary (envelope + encryptedPayload)
- Logs NEVER contain: payload plaintext, GPS coordinates, raw bytes, or PII

**Event Trace Format (JSONL):**
```jsonl
{"ts":1698604800,"event":"chunk_sent","msgId":"a3f2b1c0","seq":0,"total":5}
{"ts":1698604801,"event":"ack_received","msgId":"a3f2b1c0","seq":0}
```

### 9. Test Strategy

**Mock Transports:**
- Separate sender/receiver endpoints with simulated channel
- Configurable packet loss (0-50%), duplication, reordering
- Latency injection (10-1000ms)
- Disconnect/reconnect scenarios

**Fuzz Testing:**
- Seeded deterministic PRNG for reproducibility
- Minimum 2000 scenarios covering:
  - Loss, duplication, reordering
  - Corrupt CRC, wrong digest, total mismatch
  - Interrupt + resume, timeouts
- **Invariants:**
  - (a) NEVER PEER_RECEIVED on wrong/incomplete data
  - (b) Completed transfer: received == sent (byte equality)
  - (c) Application receives each message exactly once (no duplicates)
  - (d) Interrupted transfer completes with resume
- Mutation testing to verify fuzz catches real bugs

**Cross-Platform Validation:**
- Kotlin and Swift implement CRC32, SHA-256, chunk encode/decode
- Test vectors (synthetic data, no real GPS/PII) validated in CI

### 10. Implementation Phases

**Phase 1 (This ADR):**
- TypeScript reference implementation in `packages/ble-protocol`
- Mock transports and fuzz testing
- Test vectors in `packages/fixtures/ble`

**Phase 2 (Future):**
- React Native BLE integration
- Physical device testing (separate from mock-based protocol proof)
- End-to-end encryption key exchange

## Consequences

### Positive

- **Reliability:** CRC + digest + resume ensures message integrity even in hostile conditions
- **Privacy:** Encrypted payload opaque to relays, logs contain no sensitive data
- **Testability:** Mock transports and fuzz testing provide high confidence without physical devices
- **Cross-Platform:** Test vectors ensure TypeScript/Kotlin/Swift equivalence
- **Clear Semantics:** Distinct ACK levels prevent UI confusion (peer ≠ operator read)

### Negative

- **Complexity:** State machine and resume logic increases implementation difficulty
- **Overhead:** 12-byte header + 32-byte digest per message (acceptable for low-bandwidth)
- **Physical BLE Not Proven:** This ADR validates protocol design only; real device integration is separate

### Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Protocol bugs in production | Comprehensive fuzz testing (2000+ scenarios) |
| Cross-platform incompatibility | CI validates test vectors on all platforms |
| Privacy leak in logs | Automated redaction, event trace format with no PII |
| False PEER_RECEIVED | Strict validation: CRC + digest before ACK |

## Notes

**CRITICAL CONSTRAINTS:**
1. Offline BLE messages work without AI service calls
2. Volunteer relays NEVER see plaintext SOS content (only envelope)
3. PEER_RECEIVED ≠ "okundu" (read) in UI
4. Physical BLE success NOT claimed in this phase (mock-based proof only)
5. No secrets, PII, or real GPS in repository or logs
